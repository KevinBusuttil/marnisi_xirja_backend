# Checkout v2 deployment and acceptance

This change supports discounts, direct cart returns, externally completed Stripe/Bank Transfer payments and Tailored Experience. A negative internal balance creates a cash-refund obligation; it never creates a credit note, customer balance or voucher. Customer-facing displays use positive values and explicit purchase/return labels.

## Coordinated upgrade

1. Back up the backend database and preserve every tablet's existing outbox. Record current fiscal numbering/high-watermarks before the upgrade.
2. Deploy backend source and run `bench --site <intended-site> migrate` through the normal authorized deployment process. Request handlers do not run DDL. This implementation task uses only the marked disposable site.
3. Migration adds catalogue flags, transaction receipt metadata and service-owned checkout authorization/cash payout/event tables. Existing items become returnable once; Tailored Experience is seeded non-returnable, variable-priced, with 18% VAT. Review its configured VAT before trading. Later migrations preserve all catalogue choices and existing fiscal evidence.
4. Deploy the new Android application after the backend migration. Synchronize the catalogue and capabilities. Older backends do not advertise the new checkout actions. Existing protocol-1 outboxes and historical linked-refund evidence retain their original hashes/acknowledgements.
5. Complete physical tablet/Bixolon acceptance and refresh EXO evidence before approving use. This change adds transaction-level fiscal evidence, zero-total exchanges and unlinked returns, so historical certification/test evidence cannot certify its new behavior.

## Checkout contract and recovery

`api.fiscal.prepare_checkout` takes `{sale: <protocol-2 payload>}` and returns an opaque authorization plus `sale_num` and `cart_hash`. It validates current return eligibility, pricing, VAT and fiscal context before collecting money. The hash excludes only actual tender rows, cash change/cash tendered and the authorization field. Finalization uses the existing bridge `post_all_sales` batch envelope. The same checkout identity must never be reused for another cart.

The signed balance determines `settlement.direction` (`payment`, `cash_refund`, `none`), positive `settlement.amount`, and a stable `payout_uid` for refunds. Only incoming collections have payment rows. Cash refunds and zero-balance exchanges have no fabricated payment. Active v2 transactions receive one `record_kind: Transaction` fiscal record, including exchanges with zero payment. Protocol 1 continues payment-level numbering/evidence.

A recorded negative balance returns separate `cash_payout` proof in its acknowledgement. The immutable original acknowledgement remains `pending` forever; retrieve current proof from history or `get_cash_payout_status`. `begin_cash_payout` durably binds a stable `handover_uid` before displaying the cash instruction. `confirm_cash_payout` records confirmation using the same identity. Calls require the original cashier; selling staff have access to their own return handovers. Conflicting identities are rejected, and retries reuse the original evidence.

Pending/Review/unknown checkout outcomes do not authorize handing over cash. If a handover is interrupted, recover its existing identity and explicitly establish whether cash was already given; never automatically perform another payout. Settings suspension or fiscal-mode changes block a new handover. Confirmation of an already-started handover remains possible so an actual disbursement is not lost. Disabled-mode transactions remain nonfiscal and can refund cash; production EXO use still requires the established Live gates.

Reconciliation distinguishes `cash_refund_due`, `cash_refund_outstanding` and `cash_refunded`. It reconciles v2 signed transaction evidence against signed item totals and positive incoming payment totals, without treating a cash obligation as money already disbursed.

## Verification

Use the single frontend trigger `MARNISI_TEST_SITE=marnisi-fiscal-test.cashreturns.localhost MARNISI_REQUIRE_INTEGRATION=1 ./run_all_tests.sh`. The guarded runner refuses unmarked/non-loopback databases. Unit tests cover validation, forgery rejection, cent allocation, open prices, return eligibility, atomic rollback, stable authorization and cash-payout retries; cross-language fixtures are generated by the actual Dart implementation. Integration acceptance covers real staff HTTP sessions, concurrency, rollback, reconciliation and repeated migrations. Keep raw credentials and machine-specific site files outside both repositories.

Physical acceptance must verify ordinary receipts, return-only receipts, €70/€50 exchanges, €30/€50 cash refunds, even exchanges, partial cash/noncash collections, interrupted handovers, history copies and printer reconnection. Native Android/Bixolon transport, libraries, Bluetooth permissions and printer lifecycle must remain identical to the prior working version.
